# Техническое задание: консольный парсер DSL v1.0

## 1. Назначение и границы

Разработать консольную утилиту `dslparser` на Go 1.25.0. Утилита должна находить входные TXT-файлы, разбирать поддерживаемую версию DSL и сохранять результат рядом с каждым исходником в JSON по контракту `Contract.jsonc` версии `1.0`.

Парсер должен:

- формировать структурное построчное представление документа;
- поддерживать выбор грамматики по `@dsl-version`;
- поддерживать синтаксис, контексты и границы конструкций DSL v1.2;
- фиксировать только диагностики P001–P014 из `Errors.md` и техническую ошибку чтения входа, определённую настоящим ТЗ;
- создавать JSON и при успешном разборе, и при ошибке конкретного входного файла;
- не выполнять редакционные, содержательные, ресурсные и иные проверки, оставленные валидатору.

Не реализовывать интерпретацию, отображение, сборку учебного пакета, проверку файлов ресурсов, разрешение `@include` и семантическую валидацию документа.

## 2. Нормативные материалы и приоритет

Использовать следующие документы:

1. `DSL v1.2.md` — грамматика и правила контекстов DSL v1.2.
2. `Contract.jsonc` — структура выходного JSON, `formatVersion = "1.0"`.
3. `Errors.md` — исчерпывающий перечень DSL-диагностик, создаваемых парсером.
4. Настоящее ТЗ — порядок пакетной обработки, границы ответственности и уточнения профиля парсера.

При расхождении применять настоящий документ для определения границ парсера, не изменяя синтаксис DSL и поля JSON-контракта.

### 2.1. Уточнения профиля парсера

- Внутренность блочных `@text`, `@table` и `@multifill` не разбирать на HTML, ячейки, разделители, варианты или плейсхолдеры. Сохранять строки как `content`. Пустая строка внутри блочного `@multifill` также имеет тип `content` и `content.value = ""`; в `@text` и `@table` она имеет тип `blank`.
- Строку `---` внутри `@table` сохранять как `content`, а не как `separator`. Проверку структуры таблицы выполняет валидатор.
- Элементы `placeholder` парсер не создаёт. Для P012 разрешается только минимально распознать защищённый диапазон формы `_____{...}`, чтобы не принять его фигурные скобки за границы блока. Ответ не извлекать и корректность плейсхолдера не проверять.
- Нарушения DSL, не соответствующие P001–P014, не добавлять в `diagnostics`. Синтаксически выделяемые данные сохранять без автоматического исправления; дальнейшую допустимость проверяет валидатор.
- Если значение нельзя представить специализированным элементом контракта без выполнения отложенной проверки, сохранять остаток объявления одним элементом `content`. Не создавать `unparsed` без диагностики и не придумывать код ошибки.

## 3. Командная строка

Формат запуска:

```text
dslparser [--replace] [--depth N] <path>
```

Параметры:

| Параметр | Правило |
| --- | --- |
| `<path>` | Обязательный путь к обычному файлу или каталогу. Привести к абсолютному очищенному пути. |
| `--replace` | Необязательный флаг. Разрешает заново разобрать источник и заменить целевой JSON. По умолчанию `false`. |
| `--depth N` | Необязательная глубина обхода, где `N` — целое число `>= 0`. `0` означает только переданный каталог, `1` — каталог и один уровень подкаталогов. При отсутствии ограничения нет. Для пути к файлу параметр игнорируется. |

Не принимать неизвестные флаги, отрицательную глубину, более одного позиционного пути и отсутствующий путь. Такие ошибки являются ошибками запуска, выводятся в консоль и завершают программу до поиска файлов.

Если явно передан файл не с расширением `.txt`, завершать запуск с ошибкой. При обходе каталога игнорировать все файлы, кроме обычных файлов с расширением `.txt`. Расширение сопоставлять без учёта регистра. Символические ссылки при обходе не обрабатывать и по ссылкам на каталоги не переходить.

## 4. Сценарии использования

| Сценарий | Ожидаемый результат |
| --- | --- |
| Передан новый TXT-файл | Файл разобран; рядом создан одноимённый JSON. |
| Передан каталог | Все подходящие TXT в пределах глубины обработаны в детерминированном порядке; выведен общий итог. |
| Найден актуальный JSON, `--replace` выключен | Выполнена только проверка источника и результата; полный разбор и запись не выполняются. |
| Указан `--replace` | Источник разобран заново; целевой JSON безопасно заменён. |
| В документе есть восстанавливаемые P003–P010/P012 | Ошибки записаны в JSON; разбор продолжен; файл имеет статус `УСПЕХ`. |
| Обнаружена невосстанавливаемая ошибка структуры | В JSON сохранены диагностика, разобранная часть и лексический хвост; файл имеет статус `ОШИБКА`. |
| Файл пуст, не является DSL, имеет неверный UTF-8 или неподдерживаемую версию | Создан JSON с фатальной диагностикой; файл имеет статус `ОШИБКА`. |
| Входной файл невозможно прочитать | По возможности создан JSON с IO001; при невозможности записи ошибка осталась в консоли. |
| Существующий результат нельзя однозначно сопоставить | Без изменения файлов выведена операционная `ОШИБКА`; требуется устранить конфликт либо явно разрешить допустимую замену. |

## 5. Поиск и порядок обработки файлов

1. Определить тип `<path>` через файловую систему.
2. Для каталога выполнить ограниченный по `--depth` обход. Ошибка чтения отдельного подкаталога не должна останавливать обработку уже найденных файлов, но должна попасть в консоль и сделать итог запуска ошибочным.
3. Отсортировать TXT-файлы лексикографически по абсолютному очищенному пути. Обрабатывать последовательно в этом порядке.
4. Собрать индекс обычных `.json`-файлов из каталогов, в которых найдены TXT-файлы. Не читать JSON из иных каталогов.
5. Из существующего JSON читать только данные, необходимые для сопоставления: `formatVersion`, `document.dslVersion`, `document.metadata.documentId`.

Парсер должен обрабатывать один исходник за раз и не хранить байты всех найденных файлов в памяти одновременно.

## 6. Имя результата и сопоставление с существующим JSON

Целевой путь результата получать заменой последнего расширения исходного файла на `.json`. Результат всегда находится в каталоге исходного TXT-файла.

Имя JSON не доказывает связь с источником. Основной идентификатор связи — `@document-id`, сравниваемый без учёта регистра. SHA-256 используется для проверки неизменности точных исходных байтов.

Существующий целевой JSON считать актуальным только при одновременном выполнении условий:

- JSON корректно читается и имеет `formatVersion = "1.0"`;
- у источника однозначно извлечён `@document-id`;
- `document.metadata.documentId` совпадает с ним без учёта регистра;
- `document.dslVersion` совпадает с версией источника;
- в собранном индексе нет второго JSON с тем же `document-id`.

Если `@document-id` отсутствует или неоднозначен, повторное использование существующего JSON запрещено: связь нельзя устанавливать по имени файла.

### 6.1. Поведение режима замены

| Ситуация | `--replace=false` | `--replace=true` |
| --- | --- | --- |
| Целевого JSON нет, конфликтов `document-id` нет | Разобрать и создать JSON | Разобрать и создать JSON |
| Целевой JSON актуален | Не выполнять полный разбор; вывести `УСПЕХ`, действие `пропущен` | Разобрать и заменить JSON |
| Целевой JSON существует, но неактуален, повреждён или не сопоставлен | Не разбирать; вывести `ОШИБКА` о конфликте результата | Разобрать и заменить именно целевой JSON |
| Другой JSON в области поиска имеет тот же `document-id` | Не разбирать; вывести `ОШИБКА` неоднозначности | То же; флаг не разрешает удалять или заменять посторонний JSON |

`--replace` разрешает замену только вычисленного целевого пути. Утилита не должна удалять, переименовывать или исправлять другие JSON-файлы.

При принудительной замене всегда заново строить `document` и `lines`.

## 7. Конвейер одного файла

Выполнять этапы в следующем порядке:

1. Зафиксировать время начала попытки. Создать `processing.id`, только если для файла будет сформирован новый результат; пропуск актуального JSON не добавляет запись в `processing`.
2. Прочитать точные байты источника.
3. Вычислить `byteLength` и SHA-256 исходных байтов, включая BOM и переводы строк.
4. Проверить UTF-8, BOM и переводы строк. Не заменять повреждённые байты и не нормализовать EOL.
5. Выделить физические строки, сохранив `raw` и `eol`. UTF-8 BOM допустим только в начале файла и не входит в `raw` первой строки.
6. Разобрать первую строку и выбрать грамматику через реестр версий.
7. Выполнить лёгкое извлечение `document-id` и проверку актуального JSON. При актуальном результате и выключенной замене завершить файл без полного разбора.
8. Выполнить построчный структурный разбор, построить элементы, логические связи и диагностики.
9. Сформировать метаданные документа, признаки `hasErrors`, длительность и итоговый JSON.
10. Проверить внутренние инварианты модели перед сериализацией.
11. Безопасно записать или заменить целевой JSON.
12. Вывести результат файла в консоль.

Нельзя открывать или обнулять целевой JSON до успешного завершения чтения, разбора, проверки модели и сериализации нового результата.

## 8. Правила структурного разбора

### 8.1. Лексический слой

- Сохранять `line.raw` и `line.eol` точно по контракту.
- Для распознавания использовать строку после удаления только начальных и конечных U+0020 и TAB. Исходное значение `raw` не менять.
- Считать колонки по Unicode-кодовым точкам, начиная с 1. Байтовые индексы Go-строки не использовать как колонки.
- Учитывать регистронезависимость имён тегов и фиксированных значений, сохраняя исходное написание в `raw`.
- Снимать экранирование только для последовательностей, имеющих специальное значение в текущем контексте DSL. Не выполнять повторный разбор полученного значения.

### 8.2. Состояние разбора

Поддерживать раздельно:

- стек фигурных блоков с тегом, строкой открытия и контекстом содержимого;
- состояние неблочных областей: текущий шаг документа, активный `@task`, внутренний `@step`, блок `@variants` и текущая ветвь `@variant`;
- номер логического родителя для расчёта `parentLine` и `nestingLevel`.

Заголовки всегда имеют `parentLine = null` и `nestingLevel = 0`. Для остальных строк родителя определять по правилам выбранной версии DSL, а не по исходным отступам.

Неэкранированная строка `}` закрывает только верхний элемент стека фигурных блоков. Скобки плейсхолдера и экранированные скобки стек не изменяют.

### 8.3. Контексты и версии

Грамматика версии должна задавать:

- поддерживаемые имена тегов;
- допустимые однострочные и блочные формы;
- правила выделения параметров и свободного содержимого;
- режим содержимого блока;
- разрешённые дочерние конструкции и правила завершения неблочных областей;
- правила родителя для строки;
- условия, соответствующие P003–P014.

Запрещённое по смыслу расположение известного и синтаксически выделенного тега не диагностировать кодом, отсутствующим в `Errors.md`. Сохранить конструкцию и её фактического логического родителя, чтобы валидатор мог выдать отдельную диагностику.

Новая версия DSL должна добавляться отдельной реализацией грамматики и одной регистрационной записью. Обнаружение файлов, чтение байтов, JSON-модель, запись результата и консольный вывод при этом не изменять.

### 8.4. Восстановление после ошибки

После P003–P010 и P012 продолжать разбор, только если состояние стека и логический родитель следующей строки определяются однозначно. Ошибочную строку представить по `Contract.jsonc`, сохраняя все корректно выделенные соседние элементы.

Если невозможно однозначно определить, был ли открыт или закрыт блок, установить `fatal = true`, прекратить структурный разбор после ошибочной строки и не изменять стек предположением. P011 при EOF всегда завершает разбор файла с `fatal = true`.

Чтение и сохранение физических строк отделить от структурного разбора. Поэтому при остановке парсера все декодированные строки всё равно должны присутствовать в `lines`. Необработанный хвост представить в безопасном лексическом режиме: пустые строки — `blank`, остальные — корневой `content` с одним элементом `content`, без снятия контекстного экранирования. Наличие хвоста однозначно сопровождается предшествующей фатальной диагностикой.

## 9. Диагностики и статус файла

Все P001–P014 имеют `severity = "error"`. Код, условие и формулировка должны браться из единого реестра в коде, соответствующего `Errors.md`.

Обязательная классификация:

| Случай | Диагностика | Поведение |
| --- | --- | --- |
| Вход содержит неверный UTF-8 | P001 | `fatal=true`; `encoding=null`, `lines=[]`, `lineCount=null`; при доступных байтах сохранить `byteLength`, `sha256` и признак BOM. |
| Обнаружен одиночный CR | P002 | `fatal=true`; не преобразовывать CR; сохранить декодируемые физические строки в лексическом режиме. |
| Пустой файл или первая строка не задаёт версию | P013 | `fatal=true`; для пустого файла `lineCount=0`, `lines=[]`, `location=null`. |
| Версия выделена, но не поддерживается | P014 | `fatal=true`; сохранить прочитанное значение версии, остальные строки — в лексическом режиме. |
| EOF при непустом стеке блоков | P011 | `fatal=true`; указать открывающий тег и его место в `relatedLocations`. |
| Локальная ошибка P003–P010 или P012 с однозначным восстановлением | Соответствующий код | `fatal=false`; продолжить разбор. |
| Исходный файл невозможно прочитать | IO001 | Техническая, не DSL-диагностика; `severity="error"`, `scope="document"`, `fatal=true`, `location=null`. Попытаться записать JSON с известными `fileName` и `filePath`, остальными недоступными полями `null`. |

Не выдавать P013 дополнительно после P001 или P002: первичная ошибка уже исключает надёжный выбор грамматики.

`document.hasErrors` и `line.hasErrors` вычислять строго по правилам контракта. Идентификаторы диагностик создавать уникальными внутри результата и назначать в нормативном порядке. Одна проблема не должна порождать дубликаты одного кода на одном диапазоне.

Статус файла:

- `УСПЕХ` — JSON создан/заменён без фатальной диагностики либо актуальный JSON пропущен. Варианты P003–P010 и P012, после которых состояние однозначно восстановлено, не меняют статус на `ОШИБКА`.
- `ОШИБКА` — имеется фатальная диагностика, не удалось безопасно получить результат либо возник конфликт существующего JSON.

## 10. Выходной JSON

Выдавать обычный JSON без комментариев. Поля и допустимые значения должны соответствовать `Contract.jsonc`.

Дополнительные требования:

- `formatVersion` всегда равен `"1.0"`;
- `document.filePath` — абсолютный очищенный путь, `fileName` — его последний компонент;
- `document.sha256` — 64 шестнадцатеричных символа нижнего регистра;
- `processing.tool` — стабильное значение `"dsl-parser"`;
- `processing.version` — непустая версия исполняемого файла, заданная при сборке; значение `null` парсер не создаёт;
- `processing.startedAt` — UTC в RFC 3339 с часовым поясом `Z`;
- `durationMs` — фактическая длительность завершённой попытки обработки, включая формирование отчёта;
- массивы выводить как `[]`, а не `null`, кроме полей, где контракт прямо допускает и требует `null` при недоступности;
- JSON форматировать отступом в два пробела, завершать LF и не выполнять HTML-экранирование символов `<`, `>` и `&`;
- порядок `lines`, `elements`, `processing`, `diagnostics`, `errorIds` и `relatedLocations` должен быть детерминированным и соответствовать контракту.

Перед записью проверять ссылки `source`, `errorIds`, `parentLine`, диапазоны элементов, отсутствие пересечений и дубликатов, согласованность `nestingLevel`, `lineCount` и `hasErrors`.

Записывать результат через временный файл в целевом каталоге. Новый файл сначала полностью записать, синхронизировать и закрыть. При замене использовать резервное переименование старого файла; при ошибке установки нового файла восстановить старый. Не обнулять существующий JSON на месте.

Если создать или заменить JSON невозможно, вывести ошибку в консоль и сохранить прежний JSON без изменений. Ошибки параметров, обхода каталогов, неоднозначного сопоставления, запрета перезаписи и записи результата являются операционными: их нельзя добавлять в целевой JSON без нарушения режима замены. Все ошибки, возникшие после начала разрешённой обработки конкретного TXT и допускающие запись результата, должны находиться в его JSON.

## 11. Консольный вывод и коды завершения

Для каждого TXT вывести ровно одну итоговую строку. Строка должна содержать статус, действие, количество диагностик уровня `error`, абсолютный путь источника и краткое сообщение при ошибке.

Рекомендуемый вид:

```text
УСПЕХ action=created errors=2 path="C:\data\lesson.txt"
УСПЕХ action=skipped errors=0 path="C:\data\lesson.txt"
ОШИБКА action=failed errors=1 path="C:\data\broken.txt" message="P001: некорректная кодировка UTF-8"
```

После всех файлов вывести одну итоговую строку с полями: `found`, `parsed`, `created`, `replaced`, `skipped`, `success`, `failed`, `diagnostics` и `scanErrors`.

Коды завершения процесса:

| Код | Значение |
| --- | --- |
| `0` | Все найденные файлы имеют статус `УСПЕХ`; нефатальные диагностики допустимы. |
| `1` | Хотя бы один файл имеет статус `ОШИБКА` либо была ошибка обхода каталога. |
| `2` | Ошибка параметров запуска или исходного пути; обработка не начиналась. |

## 12. Архитектура пакетов

Собрать один Go-модуль и один исполняемый файл. Использовать только стандартную библиотеку Go.

| Пакет | Зона ответственности |
| --- | --- |
| `cmd/dslparser` | Точка входа, разбор аргументов, вызов приложения, возврат exit code. Без логики DSL. |
| `internal/app` | Оркестрация пакетного запуска, последовательность этапов, статистика и статус файла. |
| `internal/discovery` | Определение типа пути, обход с глубиной, отбор и сортировка TXT, сбор путей существующих JSON. |
| `internal/storage` | Чтение исходных байтов, SHA-256, вычисление целевого пути и безопасная запись/замена JSON. Не принимает решений о кэше. |
| `internal/cache` | Чтение минимальных заголовков существующих JSON, индекс по `document-id`, проверка актуальности и выявление конфликтов. |
| `internal/model` | Структуры JSON-контракта и методы проверки их внутренних инвариантов. Без файлового ввода-вывода. |
| `internal/diagnostics` | Реестр P001–P014 и IO001, создание диагностик, уникальные ID, порядок и привязка к диапазонам. |
| `internal/grammar` | Минимальный интерфейс грамматики, реестр поддерживаемых версий, общие типы формы тега и контекста. |
| `internal/grammar/v1_2` | Декларативное описание тегов, форм, режимов содержимого, контекстов и переходов DSL v1.2. |
| `internal/parser` | Декодирование строк, лексический разбор, машина состояний, стек блоков, восстановление, построение `lines` и метаданных через выбранную грамматику. Без консоли и записи файлов. |
| `internal/report` | Сборка полного результата, расчёт `hasErrors`, сериализация JSON. |
| `internal/console` | Форматирование строк `УСПЕХ`, `ОШИБКА` и `ИТОГ`. Без принятия решений о статусе. |

Вводить интерфейс только на границе версий грамматики и внешнего файлового доступа, необходимого для тестов. Не создавать отдельный пакет на каждый тег или диагностический код.

Функции должны выполнять одну понятную операцию. Разделять чтение, декодирование, выбор версии, разбор строки, изменение состояния, создание диагностики, сборку отчёта и запись файла. Большую функцию конвейера реализовать как последовательность небольших этапов с явным результатом каждого этапа.

Комментарии и документацию к нетривиальной логике писать на русском языке. Комментарии к экспортируемым идентификаторам должны соответствовать требованиям `go vet` и начинаться с имени идентификатора.

## 13. Требования к качеству и тестам

Обязательные проверки:

- `go test ./...`;
- `go test -race ./...`;
- `go vet ./...`;
- `go build ./cmd/dslparser` на Go 1.25.0.

Покрыть модульными тестами:

- UTF-8, BOM, LF, CRLF, одиночный CR, пустой файл и EOF без EOL;
- колонки и диапазоны с многобайтными Unicode-символами;
- все формы тегов из таблицы P005–P007;
- P001–P014, отсутствие дублей и значения `fatal`;
- открытие, закрытие, вложение и незакрытые фигурные блоки;
- автоматическое завершение `@task`, `@step` и ветвей `@variant`;
- непрозрачное содержимое `@text`, `@table`, `@multifill` и отсутствие `placeholder`;
- глубину обхода `0`, `1` и без ограничения;
- сопоставление JSON по `document-id`, SHA-256 и версии, включая дубликаты ID;
- режимы создания, пропуска, конфликта и принудительной замены;
- валидацию ссылок и инвариантов JSON-контракта;
- сохранность старого JSON при ошибке записи нового.

Добавить интеграционные golden-тесты CLI минимум для: корректного документа, документа с нефатальными ошибками, пустого файла, неверного UTF-8, неподдерживаемой версии, фатальной ошибки вложенности, актуального результата и замены устаревшего результата.

## 14. Критерии приёмки

Работа считается принятой, если:

1. Утилита корректно различает файл и каталог, соблюдает глубину и обрабатывает только TXT.
2. Для каждого обработанного входа создаётся или безопасно заменяется JSON рядом с исходником; при фатальной ошибке формируется доступный частичный результат.
3. Выход соответствует `Contract.jsonc`, включая Unicode-координаты, ссылки, порядок и признаки ошибок.
4. Парсер выдаёт только P001–P014 и IO001; остальные нарушения DSL оставляет валидатору.
5. Внутренность `@text`, `@table`, `@multifill` и плейсхолдеры не разбираются парсером.
6. Нефатальные локальные ошибки не мешают продолжению разбора и дают консольный статус `УСПЕХ`.
7. При неоднозначной структуре парсер прекращает структурный разбор без догадок, сохраняет диагностированный частичный результат и выводит `ОШИБКА`.
8. Добавление новой версии DSL не требует изменения пакетного конвейера, JSON-модели, записи файлов и консольного слоя.
9. Существующий JSON не повреждается при сбое замены.
10. Все обязательные тесты, `go vet` и сборка проходят без ошибок и внешних зависимостей.
